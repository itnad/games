# Stark Rift 오프라인 구현 설계

> 상태: 구현 기준안  
> 작성일: 2026-10-30  
> 구현 설계 고도화: 2026-11-01
> 구현 진행: 단계 4 운영·사이트 테스트, 단계 5C 시야·정찰 기억·고지대·탐지·본부 승패에 이어 단계 6A 버로우에 이어 단계 6B 다크 템플러/옵저버 영구 은폐·탐지, 드롭십/셔틀/오버로드 수송, 선행 기술·레어 변태·특수 연습·저장 호환을 구현했다 (`docs/stark-rift-stage6b.md`). 단계 6C 고스트·레이스 능동 클로킹·에너지·선행 생산/연구·저장 12 호환까지 이어서 연결했다 (`docs/stark-rift-stage6c.md`). 단계 6D는 시즈 모드 연구·전환/해제·지상 범위 포격·저장 13 호환을 연결했다 (`docs/stark-rift-stage6d.md`). 단계 6E는 러커 연구·변태/취소·잠복 직선 범위 공격·저장 14 호환을 연결했다 (`docs/stark-rift-stage6e.md`). 단계 6F는 아비터 생산·주변 아군 자동 은폐장·탐지 대응·저장 15 호환을 연결했다 (`docs/stark-rift-stage6f.md`). 단계6G는 리콜·스테이시스 연구/시전·상태 연동·저장16 호환을 연결했다 (`docs/stark-rift-stage6g.md`). 추가 기술·적 전략 AI와 실제 기기 검증은 후속 대상.
> 기반 검토: `docs/stark-rift-foundation-review.md` (초기 계약의 검증 범위와 미구현 경계)
> 상위 기획: `docs/stark-rift-game-design.md`

## 1. 목표와 경계

이 문서는 확정된 게임 기획을 새 코드로 구현하기 위한 기술 구조와 작업 순서를 정한다.

- 이전 Stark Rift 또는 Claude 초안의 코드와 구조를 재사용하지 않는다.
- 별도의 v2나 시제품 프로젝트를 만들지 않고 최종 `/stark-rift` 경로를 기준으로 새로 구현한다.
- 초기 구현과 검증은 플레이어 대 AI 오프라인 1대1에 집중한다.
- 최종 게임 화면은 모바일 세로 모드만 지원하며 1:2:1 레이아웃을 기준으로 한다. 가로에서는 입력을 차단하고 세로 전환 안내를 표시한다.
- 전투 규칙과 저장 형식은 결정적이어야 한다. 같은 초기 상태와 명령은 같은 결과를 내야 한다.
- 렌더링, UI와 시뮬레이션을 분리한다.
- 불완전한 화면을 Paperoid 메인과 빠른 시작에 노출하지 않는다.
- 사용자에게 공개되는 단계에서는 임시 도형, 개발자 문구와 미완성 조작을 남기지 않는다.

## 2. 기술 선택

### 2.1 애플리케이션

- 기존 Next/Vinext와 React 구성을 유지한다.
- React는 상단 정보 패널, 하단 명령창, 메뉴, 설정과 접근성 UI를 담당한다.
- 게임 전장 렌더링은 React DOM에서 분리한다.
- 현재 저장소의 TypeScript 엄격 모드를 유지한다.

### 2.2 전장 렌더링

- WebGL 렌더러는 구현 시점의 안정된 PixiJS 8 계열을 사용한다.
- React 전용 Pixi 래퍼를 사용하지 않고 클라이언트 컴포넌트에서 Pixi 애플리케이션 수명주기를 직접 관리한다.
- WebGL2를 필수로 사용하고 지원하지 않는 기기에는 지원 불가 안내를 제공한다.
- 메인 전장과 미니맵은 동일한 렌더 데이터에서 그린다.
- 스프라이트 아틀라스, 객체 풀과 화면 밖 객체 제외를 기본으로 한다.

### 2.3 시뮬레이션

- 게임 시뮬레이션은 전용 Web Worker에서 실행한다.
- 고정 틱은 초당 20회, 한 틱은 50ms다.
- 화면은 시뮬레이션 스냅샷 사이를 보간해 60fps로 표시한다.
- 게임 규칙에서 `Date.now`, `performance.now`와 `Math.random`을 사용하지 않는다.
- 좌표, 속도와 시간은 결정성을 위해 정수 또는 고정소수점으로 저장한다.
- Web Worker를 사용할 수 없는 환경에서는 경기를 시작하지 않고 지원 불가 안내를 제공한다.

### 2.4 로컬 데이터

- 진행 중 경기, 설정과 리플레이는 IndexedDB에 저장한다.
- 저장 데이터는 명시적인 스키마 버전과 엔진 버전을 가진다.
- 압축은 브라우저의 `CompressionStream`을 우선 사용하고 지원되지 않으면 비압축 저장을 허용한다.

### 2.5 버그 리포트

- 신고 메타데이터와 상태는 기존 D1을 사용한다.
- 장면 이미지, 상태 스냅샷과 진단 기록은 R2를 사용한다.
- 실제 신고 기능 구현 전에 `.openai/hosting.json`과 Worker 바인딩에 R2를 추가한다.

### 2.6 지원 환경과 기준 기기

- 공개 지원 범위는 배포 시점 기준 Android Chrome과 iOS Safari의 최근 주요 2개 버전이다.
- 데스크톱 Chrome은 개발·리플레이·관리 화면 검증용으로 지원한다.
- 성능 기준 기기는 2022년급 중급 모바일, 6GB 메모리, WebGL2, 390×844 CSS 픽셀과 최대 DPR 3 수준으로 정의한다.
- 단계 2 시작 시 실제 Android·iOS 기준 기기를 각 1대 이상 기록하고 이후 성능 보고서에서 같은 기기를 유지한다.
- WebGL2, Worker, IndexedDB와 필요한 저장 공간을 시작 화면에서 확인하고 부족한 환경에는 구체적인 지원 안내를 표시한다.

## 4. 시뮬레이션 상태

### 4.1 시뮬레이션 상태

게임 결과에 영향을 주는 핵심 상태는 렌더링·카메라·선택 상태와 분리한다.

```ts
type SimulationState = {
  schemaVersion: number;
  engineVersion: string;
  dataVersion: string;
  tick: number;
  seed: number;
  rngStreams: RngStreamState[];
  counters: SimulationCounters;
  commandState: CommandSchedulerState;
  phase: "setup" | "running" | "paused" | "finished";
  map: MapState;
  players: PlayerState[];
  entities: EntityStore;
  projectiles: ProjectileStore;
  gameplayEffects: GameplayEffectStore;
  scheduledEvents: ScheduledEventQueue;
  ai: AiRuntimeState[];
  outcome: MatchOutcome | null;
};

type SimulationCounters = {
  nextEntityId: number;
  nextProjectileId: number;
  nextEventId: number;
};

type CommandSchedulerState = {
  lastAcceptedSequenceByPlayer: number[];
  nextInternalCommandId: number;
  pending: GameCommand[];
};

type RngStreamState = {
  id: "combat" | "ai" | "map" | "rules";
  algorithm: string;
  words: number[];
};
```

- 엔티티 ID는 경기 안에서 증가하는 정수다.
- 삭제된 ID를 같은 경기에서 재사용하지 않는다.
- 렌더러는 엔티티 ID를 기준으로 스프라이트를 재사용한다.
- 유닛과 건물의 변경 가능한 상태는 데이터 정의와 분리한다.
- 자주 접근하는 위치, 체력, 소유자와 상태 플래그는 연속 배열 또는 TypedArray로 저장한다.
- 생산 대기열, 기술 상태와 탑승 목록처럼 희소한 데이터는 별도 구조로 둔다.
- 명령 로그와 렌더 전용 파티클은 `SimulationState`에 넣지 않는다.
- 상태 체크섬은 `SimulationState`의 게임 결과 관련 필드만 대상으로 한다.

### 4.2 세션과 영속 상태

카메라와 선택처럼 게임 결과에 영향을 주지 않는 상태는 별도로 저장한다.

```ts
type SessionState = {
  camera: CameraState;
  selection: SelectionState;
  openPanel: UiPanelId | null;
};

type PersistenceEnvelope = {
  formatVersion: number;
  engineVersion: string;
  dataVersion: string;
  savedAt: string;
  simulation: SimulationState;
  session: SessionState;
  recentCommands: GameCommand[];
  checksum: string;
};
```

- 카메라와 UI 패널은 시뮬레이션 체크섬에서 제외한다.
- 부대 슬롯의 구성, 대열, 태세와 자동 기술 설정은 명령 결과에 영향을 주므로 `SimulationState.players`에 둔다.
- 현재 화면 선택과 카메라는 세션 상태에 둔다.
- 조작·그래픽·음향·접근성 설정은 경기 저장 봉투가 아니라 별도 `settings` 저장소에 둔다.
- 저장 시 Worker의 특정 틱 상태와 메인 스레드 세션 상태를 하나의 봉투로 묶는다.

### 4.3 좌표와 시간

- 1타일을 256단위로 표현하는 고정소수점 좌표를 사용한다.
- 각도는 8방향 인덱스 또는 정수 각도로 저장한다.
- 모든 지속시간은 틱 단위로 변환한다.
- 30초 정찰 정보는 600틱으로 저장한다.
- 피해, 보호막, 에너지와 자원은 정수 연산을 우선한다.
- 고정소수점 나눗셈은 0 방향으로 절삭한다.
- 게임 규칙 계산에서 암묵적인 부동소수점 반올림에 의존하지 않는다.
- 인구수는 0.5 단위를 정수로 표현하기 위해 `supplyHalf` 단위를 사용한다. 저글링 1기는 1, 마린 1기는 2로 저장한다.
- 좌표와 자원은 JavaScript 안전 정수 범위 안에서 계산하며 비트 연산에 의한 32비트 잘림을 피한다.
- 한 틱 이동량이 1/256타일보다 작은 유닛은 축별 이동 나머지를 상태에 누적해 저속 이동이 사라지지 않게 한다.
- 원작 시간 단위를 20Hz 틱으로 바꾼 뒤 50% 규칙을 적용하고, 최종 값은 최소 1틱을 보장하며 가장 가까운 정수 틱으로 반올림한다.

### 4.4 난수와 체크섬

- 경기 시작 시 하나의 명시적인 시드를 사용한다.
- 시뮬레이션용 난수 생성기를 직접 제공한다.
- AI 전략 선택과 전투 확률은 용도가 분리된 난수 스트림을 사용한다.
- 렌더링 장식과 파티클은 게임 결과에 영향을 주는 난수 스트림을 사용하지 않는다.
- 난수 생성기는 `Uint32` 연산 기반의 고정 알고리즘을 사용하고 알고리즘 ID를 저장 데이터에 기록한다.
- 스트림은 전투 확률, AI 전략, 지도 배치와 기타 규칙으로 분리해 한 시스템의 난수 소비가 다른 시스템의 결과를 바꾸지 않게 한다.
- 체크섬은 엔티티 ID 순서와 고정된 필드 순서로 직렬화한 뒤 계산한다.
- `Map`과 객체의 삽입 순서에 의존하지 않는다.
- 체크섬 알고리즘과 버전도 저장·리플레이 헤더에 기록한다.
- 현재 난수 스트림 상태, 다음 엔티티·이벤트 ID, 미래 명령, AI 전략·기억과 결과에 영향을 주는 예약 작업은 모두 저장과 체크섬 대상이다.
- 경로 캐시처럼 완전히 재생성 가능한 값은 저장에서 제외할 수 있지만, 복원 뒤 첫 틱의 결과가 달라지지 않는 테스트를 통과해야 한다.

### 4.5 엔티티 저장소와 수명주기

초기 구현은 외부 ECS를 도입하지 않고 Stark Rift 규칙에 맞는 구조를 사용한다.

- 위치, 속도, 체력, 소유자, 상태 비트처럼 대부분의 틱에서 읽는 값은 구조별 배열(SoA)과 TypedArray에 둔다.
- 생산 대기열, 탑승 목록, 기술 재사용 시간처럼 일부 엔티티만 가지는 값은 ID 기반 희소 저장소에 둔다.
- 유닛·건물과 투사체 풀을 분리하고, 늘어날 때는 기존 용량의 2배로 확장한다.
- 엔티티 ID와 물리 배열 슬롯의 대응은 명시적인 테이블로 관리한다. 삭제한 슬롯은 재사용할 수 있지만 엔티티 ID는 재사용하지 않는다.
- 물리 배열 순서와 무관한 정렬된 활성 ID 목록을 유지하고, 규칙 시스템과 체크섬은 이 목록으로 순회한다.
- 한 경기의 초기 안전 한도는 유닛·건물 2,048개, 투사체 4,096개, 예약 이벤트 8,192개로 두고 초과 시 진단 오류를 기록한다.

엔티티 상태는 다음 전이를 따른다.

| 대상 | 상태 | 허용 전이 |
|---|---|---|
| 유닛 명령 | `idle`, `move`, `attackMove`, `focusAttack`, `hold`, `patrol`, `load`, `unload`, `cast` | 검증된 새 명령, 목표 소멸, 도착 또는 행동 완료 |
| 일꾼 작업 | `idle`, `moving`, `gathering`, `returning`, `constructing`, `repairing` | 자원·건설 상태와 사용자 명령에 따라 전이 |
| 건물 | `planned`, `constructing`, `active`, `morphing`, `destroyPending` | 자원 예약, 건설 진행, 변태·파괴 처리 |
| 수송 대상 | `world`, `boarding`, `cargo`, `unloading`, `destroyPending` | 수송선과 탑승 위치가 함께 확정될 때 원자적으로 전이 |
| 상태 기술 | `inactive`, `activating`, `active`, `deactivating` | 에너지·명령·금지 상태 검사 후 전이 |

- 한 엔티티는 틱 안에서 상충하는 두 수명주기 상태를 동시에 갖지 않는다.
- 변태·합체는 기존 ID의 임의 변경이 아니라 명시적인 소스 제거와 결과 생성 이벤트로 처리한다.
- 수송선 파괴와 탑승 유닛 소멸은 하나의 이벤트 묶음으로 처리해 중간 상태가 저장되지 않게 한다.
- `destroyPending` 엔티티는 같은 틱의 동시 피해 계산에는 남지만 다음 틱으로 넘어가기 전에 반드시 정리한다.

## 5. 명령 모델

UI와 AI는 같은 명령 형식을 사용한다.

```ts
type GameCommand = {
  sequence: number;
  issuedTick: number;
  executeTick: number;
  playerId: number;
  source: "player" | "ai" | "tutorial";
  kind: CommandKind;
  entityIds: number[];
  target?: CommandTarget;
  payload?: CommandPayload;
};
```

필수 명령 종류는 다음과 같다.

- 이동
- 공격이동
- 집중공격
- 정지
- 위치 사수
- 순찰
- 대열 변경
- 전투 태세 변경
- 집결지 설정
- 생산과 반복 생산
- 생산 취소
- 건물 배치와 건설 취소
- 연구와 연구 취소
- 기술 수동 시전
- 자동 기술 토글
- 클로킹, 버로우와 시즈 모드 토글
- 탑승, 전체 하차와 개별 하차
- 항복

모든 명령은 시뮬레이션에 들어가기 전에 소유권, 자원, 사거리, 현재 상태와 선행 조건을 검증한다. 잘못된 명령은 상태를 바꾸지 않고 UI에 구조화된 실패 이유를 돌려준다.

- 명령은 `(executeTick, playerId, sequence)` 순으로 안정 정렬한다.
- 같은 플레이어의 `sequence`는 경기 동안 증가하며 재사용하지 않는다.
- 사람의 명령은 다음 실행 가능한 틱, AI 명령은 난이도별 반응 지연 이후 틱에 적용한다.
- 같은 명령을 다시 수신하면 `sequence`를 기준으로 한 번만 처리한다.
- `commandState`는 플레이어별 마지막 승인 sequence, 실행 대기 명령과 다음 내부 명령 ID를 저장해 복원 뒤에도 중복 방지가 이어지게 한다.
- 명령 실패는 `not_owner`, `invalid_target`, `out_of_range`, `blocked`, `insufficient_resource`, `missing_prerequisite`, `invalid_state`처럼 고정된 코드로 반환한다.
- 표시 문구는 UI에서 실패 코드와 상황값을 조합해 만든다.
- 사용자가 새로 내린 이동·공격·정지 명령은 해당 유닛의 기존 이동 계열 명령을 교체한다. 생산·연구·예약 이벤트처럼 독립된 작업은 명시적인 취소 명령이 있을 때만 제거한다.
- 명령 적용 중 일부 엔티티만 유효한 경우 전부 거부할지 유효 대상만 실행할지를 `CommandKind`별로 고정하고 승인 결과에 실행된 ID를 반환한다.

## 6. 시스템 실행 순서

각 틱은 같은 순서로 실행한다.

1. 현재 틱에 예약된 사람·AI 명령 정렬, 검증과 적용
2. 건설, 생산, 연구와 자원 예약 갱신
3. 자원 채취와 반납
4. 경로와 대열 목표 갱신
5. 이동, 충돌과 지역 회피
6. 시야, 전장의 안개와 탐지 갱신
7. 자동 표적과 자동 기술 후보 평가
8. 기본 공격, 투사체 도착과 기술 효과 이벤트 생성
9. 같은 틱의 피해, 회복과 상태 효과를 안정된 순서로 적용
10. 사망, 변태, 합체, 탑승과 하차 처리
11. 본부 건물과 승패 조건 검사
12. AI가 현재까지 볼 수 있는 정보로 이후 틱의 명령 생성
13. 리플레이 명령·주요 AI 결정 기록
14. 렌더 스냅샷과 UI 이벤트 생성

같은 틱에 마지막 본부 건물이 모두 파괴되면 무승부로 처리할 수 있도록 승패 검사는 모든 피해와 사망 처리가 끝난 뒤 한 번 실행한다.

- 시스템마다 엔티티를 ID 오름차순으로 순회한다.
- 같은 틱에 발생한 공격과 기술은 먼저 이벤트로 모은 뒤 적용해 순회 순서가 생존 여부를 바꾸지 않게 한다.
- 사망 예정 엔티티는 틱 종료 처리 전까지 ID와 충돌 정보를 유지하되 새 명령과 표적 후보에서는 제외한다.
- AI가 생성한 명령은 현재 틱에 즉시 적용하지 않고 난이도별 `executeTick`에 예약한다.

## 7. 데이터 정의

### 7.1 유닛과 건물

유닛과 건물은 코드 분기보다 데이터 정의를 우선한다.

```ts
type UnitDefinition = {
  id: string;
  faction: FactionId;
  mineralCost: number;
  gasCost: number;
  supplyHalf: number;
  buildTicks: number;
  maxHealth: number;
  maxShield: number;
  armor: number;
  moveSpeed: number;
  sightRange: number;
  detectionRange: number;
  collisionRadius: number;
  cargoSize: number;
  weapons: WeaponDefinition[];
  abilities: AbilityId[];
  prerequisites: Requirement[];
};
```

- 원작 수치를 별도 원본 표로 기록한다.
- 50% 시간 규칙은 정의를 덮어쓰지 않고 변환 단계에서 적용한다.
- 밸런스 조정값은 원본과 차이를 확인할 수 있는 패치 레이어로 관리한다.
- 모든 ID, 선행 조건과 생산 건물 참조는 빌드 시 검증한다.
- 종족별 데이터 파일은 동일한 타입을 사용한다.
- 유닛 크기는 `small | medium | large`, 피해 형식은 `normal | concussive | explosive`로 명시해 브루드워의 크기별 피해 배율을 데이터로 계산한다.
- 무기는 지상·공중 대상, 발사 주기, 투사체 속도, 범위 피해 단계와 공격 횟수를 각각 가진다.
- 원본 수치 표, 50% 시간 변환 결과와 모바일 조정 패치를 빌드 결과에 함께 남겨 수치의 출처를 추적할 수 있게 한다.

### 7.2 지도 정의

지도는 이미지가 아니라 규칙 데이터와 장식 데이터를 분리해 저장한다.

```ts
type MapDefinition = {
  id: string;
  widthTiles: number;
  heightTiles: number;
  terrain: Uint8Array;
  height: Uint8Array;
  walkable: Uint8Array;
  buildable: Uint8Array;
  spawnPoints: MapPoint[];
  resourceNodes: ResourceNodeDefinition[];
  regions: RegionDefinition[];
  symmetry: "none" | "rotational-180";
};
```

- 크립과 파일런 동력은 정적 지도 데이터가 아니라 경기 중 파생되는 필드다.
- 경사로, 고지대 경계, 좁은 통로와 확장 후보 지역은 명시적인 영역 ID를 가진다.
- `균열 분지`의 180도 대칭은 자원량, 이동 거리와 건설 가능 면적까지 자동 검증한다.
- 스폰에서 각 자원 거점까지의 최단 거리와 중앙·우회 경로 길이를 빌드 시 보고서로 만든다.

### 7.3 능력

- 기술은 대상 종류, 사거리, 에너지 비용, 효과, 자동 시전 조건과 중복 방지 키를 가진다.
- 수동 시전과 자동 시전은 같은 효과 실행 코드를 사용한다.
- 자동 시전은 목표 평가기만 별도로 둔다.
- 클로킹, 버로우와 시즈 모드는 상태 머신으로 구현한다.
- 범위 효과는 시전 예약과 적용 영역을 분리해 중복을 방지한다.

### 7.4 데이터 빌드와 검증

- 런타임은 사람이 편집하는 원본을 직접 읽지 않고 검증·정규화된 단일 데이터 번들을 읽는다.
- ID 중복, 순환 선행 조건, 존재하지 않는 생산처·기술·무기, 음수 비용과 지도 밖 배치를 빌드 실패로 처리한다.
- 데이터 번들 해시를 `dataVersion`으로 사용한다.
- 밸런스 변경은 데이터 번들만 바꿔도 리플레이 호환 여부를 판단할 수 있어야 한다.

## 8. 이동과 경로 탐색

### 8.1 전역 경로

- 96×96 지도를 지형과 건물 배치를 반영하는 탐색 격자로 변환한다.
- 탐색 격자는 0.5타일 간격을 기준으로 하며 96×96 지도에서 192×192 셀이다.
- 지상 유닛은 A* 기반 경로를 사용한다.
- 같은 목적지로 이동하는 부대는 전역 경로를 공유한다.
- 공중 유닛은 이동 불가 지형을 무시하고 지도 경계만 검사한다.
- 건물 완성, 파괴와 변태 시 관련 경로 캐시만 무효화한다.
- 한 틱의 새 A* 탐색은 기본 4건, 최대 확장 노드는 합계 8,000개로 제한한다. 남은 요청은 우선순위 큐에서 다음 틱에 이어간다.
- 사용자 직접 명령, 교전 중 재탐색, AI 장거리 이동 순으로 우선한다.
- 같은 부대·목적 셀·이동 크기 등급·장애물 버전 조합은 경로를 공유한다.
- 경로 계산 대기 중에는 마지막 유효 경로를 유지하고, 경로가 없으면 직선 이동을 시도하지 않는다.

### 8.2 지역 이동

- 자유 이동과 유닛 충돌을 위해 공간 해시를 사용한다.
- 공간 해시 셀은 2×2타일을 기준으로 하고 대형 유닛은 겹치는 모든 셀에 등록한다.
- 가까운 유닛만 지역 회피 계산에 포함한다.
- 근접 유닛은 목표 주위의 사용 가능한 공격 위치를 예약한다.
- 원거리 유닛은 최대 사거리와 대열 오프셋을 함께 고려한다.
- 도달 불가능한 목적지는 가장 가까운 유효 위치로 보정한다.
- 지역 회피는 결정적인 이웃 ID 순서와 정수 가중치를 사용한다.
- 유닛이 20틱 이상 의미 있게 전진하지 못하면 막힘 점수를 올리고, 대열 재배치 후에도 실패하면 전역 경로를 다시 요청한다.

### 8.3 대열

- 전열, 종대와 분산 대열의 오프셋 생성기를 분리한다.
- 복수 부대 선택 시 부대별 도착 영역을 먼저 나누고 각 부대 안에서 오프셋을 계산한다.
- 좁은 통로를 감지하면 종대로 압축하고 통과 후 원래 대열로 복귀한다.
- 느린 유닛에 전체 속도를 맞추지 않고 목적지에서 대열을 완성한다.
- 대열 목적지는 지형과 충돌을 검사해 가장 가까운 유효 셀로 개별 보정한다.
- 부대 경로의 선두점을 공유하되 유닛마다 독립적인 재탐색을 남발하지 않는다.

## 9. 시야와 전장의 안개

- 플레이어마다 현재 시야, 탐색 완료와 탐지 영역을 별도 비트셋으로 저장한다.
- 시야 격자는 0.5타일 셀을 사용하고, 시야 반경별 원형 마스크를 시작 시 캐시한다.
- 현재 시야는 유닛·건물별 기여도 카운트를 사용해 추가·제거한다.
- 시야 셀 카운트는 `Uint16Array`, 탐색 완료는 비트셋으로 저장한다.
- 지형 고도와 경사로를 시야 계산에 포함한다.
- 적 유닛의 마지막 위치와 만료 틱을 별도 정보로 저장한다.
- 적 건물의 마지막 확인 상태는 다시 정찰할 때까지 유지한다.
- 탐지되지 않은 은폐·버로우 유닛은 표적 후보와 렌더 스냅샷에서 제외한다.
- 렌더러는 시야 텍스처만 받고 숨겨진 실제 적 상태를 받지 않는다.
- 이동해 이전 마스크의 경계를 벗어난 유닛, 생성·파괴된 유닛과 시야 범위가 바뀐 유닛만 더티 목록에 넣는다.
- 전장의 안개 텍스처는 더티 사각형만 갱신하며 전체 192×192 셀을 매 틱 다시 계산하지 않는다.
- 마지막 적 위치는 `entityId`, 마지막 확인 타입·위치·체력 구간과 `expiresTick`만 저장하고 실제 숨은 엔티티를 참조하지 않는다.

오프라인 게임에서도 렌더러와 UI에는 플레이어가 볼 수 있는 정보만 전달해 이후 온라인 전환 시 경계를 유지한다.

## 10. Web Worker 통신

모든 메시지는 다음 봉투를 사용한다.

```ts
type WorkerEnvelope<K extends string, P> = {
  protocolVersion: number;
  messageId: number;
  kind: K;
  payload: P;
};
```

### 10.1 UI에서 Worker로

| `kind` | 핵심 payload | 응답 |
|---|---|---|
| `init` | 데이터 버전, 지도, 시드, 플레이어 설정 | `ready` |
| `commandBatch` | 명령 배열, UI가 본 마지막 틱 | 명령별 `commandAck` |
| `releaseRenderBuffer` | 사용을 끝낸 버퍼 ID | 없음 |
| `pause`, `resume` | 요청 사유 | `phaseChanged` |
| `saveSnapshot` | 요청 ID | `saveSnapshotReady` |
| `loadSnapshot` | 저장 봉투 | `snapshotLoaded` 또는 오류 |
| `replaySeek` | 목표 틱 | 진행률과 최종 스냅샷 |
| `debugMetrics` | 측정 구간 | `metrics` |
| `dispose` | 없음 | `disposed` |

### 10.2 Worker에서 UI로

| `kind` | 용도 |
|---|---|
| `ready` | 프로토콜·데이터 호환 확인과 초기 틱 전달 |
| `commandAck` | 명령 수락, 실행 틱 또는 고정 실패 코드 전달 |
| `renderSnapshot` | 이전·현재 틱의 가시 엔티티, 투사체와 시야 전달 |
| `uiState` | 자원, 인구수, 생산, 선택 상세와 부대 슬롯 전달 |
| `notification` | 피격, 생산 완료, 명령 실패와 승패 알림 전달 |
| `saveSnapshotReady` | 체크섬을 포함한 원자적 저장 상태 전달 |
| `fatalError` | 복구 가능 여부, 오류 코드와 진단 ID 전달 |
| `metrics` | 틱 시간, 큐 길이, 엔티티 수와 경로 예산 전달 |

### 10.3 스냅샷과 흐름 제어

- SharedArrayBuffer는 초기 구현에서 사용하지 않는다. 교차 출처 격리 없이 동작하는 TypedArray 이중 버퍼와 Transferable을 사용한다.
- 스냅샷은 `tick`, `previousTick`, `bufferId`, `createdAtFrame`과 가시 엔티티 배열을 가진다.
- 위치·방향·애니메이션·체력 구간은 병렬 TypedArray로 보내며 숨은 적의 실제 상태는 포함하지 않는다.
- Worker는 기본 20Hz로 스냅샷을 만들되 메인 스레드가 버퍼를 반환하지 않으면 가장 오래된 미전송 화면을 버리고 최신 상태를 우선한다.
- 메인 스레드는 이미 표시한 틱보다 오래된 스냅샷을 폐기한다.
- 렌더가 끝난 버퍼는 `releaseRenderBuffer`로 Worker에 반환하며, 반환하지 않은 버퍼를 다시 전송하지 않는다.
- `uiState`는 값이 바뀌었을 때 또는 최대 5Hz로 보내 DOM 갱신을 제한한다.
- 명령은 작은 일반 객체로 보내고 대용량 상태만 Transferable을 사용한다.
- 프로토콜 버전 불일치는 경기를 시작하지 않고 호환 오류 화면과 복구 가능한 저장본 정보를 표시한다.

### 10.4 Worker 장애 복구

- 메인 스레드는 마지막 정상 스냅샷, 마지막 저장 이후 명령과 최근 Worker 상태 신호를 보관한다.
- Worker가 종료되거나 2초 동안 응답하지 않으면 경기를 자동 일시정지한다.
- 최신 검증 저장본을 새 Worker에 로드하고 이후 확인된 명령을 재적용해 마지막 확인 틱까지 복구한다.
- 한 경기에서 자동 복구가 두 번 실패하면 반복 재시작하지 않고 오류 코드와 버그 신고 버튼을 표시한다.

## 11. 렌더링 구조

PixiJS 장면은 다음 레이어 순서를 사용한다.

1. 지형 타일
2. 균열, 장식과 자원 지형
3. 건물 그림자
4. 건물과 자원
5. 지상 유닛
6. 공중 유닛
7. 투사체와 전투 효과
8. 선택 링, 명령과 기술 범위
9. 전장의 안개
10. 피해, 상태와 경고 표시

- 카메라는 월드 좌표와 화면 좌표 변환만 담당한다.
- 입력 판정은 렌더 스프라이트가 아니라 엔진에서 받은 가시 엔티티 히트 영역을 사용한다.
- 광역 확대에서는 애니메이션 빈도, 파티클과 텍스트를 줄인다.
- 미니맵은 지형 캐시 위에 가시 엔티티와 카메라 영역만 갱신한다.
- 게임 장면 캡처는 렌더러의 별도 RenderTexture와 HUD 요약 레이어로 만든다.
- 스프라이트 아틀라스 한 장은 최대 4,096×4,096로 제한하고, 종족·환경·효과 묶음으로 분리한다.
- 시작 화면과 선택한 종족의 핵심 자산만 먼저 불러온다. 초기 필수 전송량은 압축 8MB 이하, 한 경기의 전체 자산은 35MB 이하를 목표로 한다.
- 저사양 기준 게임 탭의 최대 메모리는 160MB, GPU 텍스처는 96MB를 목표로 하며 초과 시 효과·고해상도 아틀라스 순으로 낮춘다.
- WebGL 컨텍스트가 사라지면 시뮬레이션을 일시정지하고 자산과 장면을 재구성한다. 10초 안에 실패하면 저장 후 지원 안내를 표시한다.
- 자산 로드는 매니페스트 해시를 검증하고 실패한 묶음만 최대 2회 다시 요청한다.

## 12. React UI와 입력

### 12.1 UI와 제스처

- 1:2:1 레이아웃은 CSS Grid로 구성한다.
- 메인 전장 크기는 선택 메뉴와 기술 목록 전환 중 변하지 않는다.
- 터치 제스처는 포인터 이벤트를 사용해 마우스 테스트도 가능하게 한다.
- 개별 선택, 길게 눌러 그룹 선택, 카메라 드래그와 공격이동 스와이프를 하나의 제스처 상태 머신에서 구분한다.
- 터치 임계값은 설정값으로 분리한다.
- 5개 부대 슬롯과 자동 기술 설정은 React UI 상태가 아니라 경기 상태에 저장한다.
- 가로 화면에서는 플레이를 지원하지 않는다. 가로 전환 시 즉시 일시정지하고 전체 게임 입력을 차단한다. 가로 상태의 최초 접속도 세로 전환 안내를 표시한다.
- 세로 복귀 시 카메라 중심·선택·슬롯과 경기 상태를 유지하고 자동 재개하지 않는다. 사용자의 명시적인 재개만 허용한다. 진행 중 터치는 회전 시 취소한다.
- 세로 화면 내 뷰포트 크기 변경 시에도 카메라 중심과 선택 상태를 유지한다.
- 웹에서는 52 CSS 픽셀을 52dp 기준으로 사용하고 모든 핵심 버튼의 실제 터치 영역을 그 이상으로 유지한다.

제스처 판정은 다음 상태 머신 하나에서 처리한다.

```text
idle
 ├─ pointer down on unit/slot → tapPending → tap | groupPreview | attackSwipe
 ├─ pointer down on terrain   → cameraPan
 ├─ pointer down on minimap   → minimapPan
 ├─ second pointer            → pinchZoom
 └─ active command            → targetingCommand
```

- `pointerId`별 시작 위치·시간·대상을 기록하고 포인터 캡처를 사용한다.
- `pointercancel`, 캡처 상실, 앱 백그라운드 전환 시 미완료 명령을 취소하고 카메라 이동만 종료한다.
- 250ms 이내 선택 완료를 응답 목표로 삼는다. 움직임 없이 300ms 전에 놓으면 개별 선택, 300ms 이상 누르면 같은 종류 최대 10기 그룹 미리보기로 판정하며, 그전에 이동량이 기준을 넘으면 드래그로 전환한다.
- 선택된 유닛에서 시작해 최소 거리 이상 스와이프하면 공격이동이며 종료 지점을 목적지로 사용한다.
- 활성 명령 모드에서는 카메라 제스처보다 대상 지정 규칙을 우선하고 취소 버튼을 항상 표시한다.
- 부대 슬롯 가로 훑기는 복수 선택, 세로 스와이프는 공격이동으로 판정하되 방향 편차 한계를 설정값으로 둔다.
- 핀치가 시작되면 같은 포인터에서 대기하던 탭·명령을 취소해 의도하지 않은 이동을 막는다.
- 접근성 입력도 터치와 동일한 `GameCommand`로 변환해 별도 규칙 경로를 만들지 않는다.

### 12.2 음향, 진동과 접근성

- 음향 관리자는 시뮬레이션의 의미 이벤트를 받아 음악, 음성, 효과음과 진동으로 변환하며 게임 상태를 직접 읽거나 바꾸지 않는다.
- 음악은 평시·긴장·교전 상태 사이를 즉시 교체하지 않고 짧은 크로스페이드로 전환한다.
- 본부 공격, 생산 완료와 자원 부족 같은 음성 경고는 우선순위와 재생 억제 시간을 두어 겹침을 막고 같은 한국어 문구를 자막으로 표시한다.
- 선택, 명령 오류, 공격 명령과 본부 피격 진동 패턴을 구분한다. 진동 미지원 환경에서는 시각 피드백만 사용한다.
- 큰 글자 모드는 전장 영역을 줄이지 않고 상·하단 패널 안에서 정보 밀도와 스크롤을 조정한다.
- 색각 보정은 팀 색만 바꾸지 않고 아이콘 모양과 테두리를 함께 사용한다.
- 흔들림·섬광·애니메이션 감소 설정은 렌더 효과에 적용하며 시뮬레이션 시간과 판정에는 영향을 주지 않는다.
- 음량, 진동, 좌우 버튼 교환과 접근성 설정은 경기 저장과 분리된 `settings` 저장소에 즉시 반영한다.

## 13. AI 구조

AI도 플레이어와 동일한 `GameCommand`를 생성한다.

### 13.1 정보 계층

- 이동 유닛 정보는 현재 시야와 최근 30초 마지막 위치까지만 AI 기억에 입력한다.
- 적 건물, 지형과 자원은 플레이어와 같은 규칙으로 마지막 확인 상태를 기억하고 재정찰 시 갱신한다.
- 실제 월드 상태를 AI 계획기에 직접 전달하지 않는다.
- 정보에는 확인 시각과 신뢰도를 저장한다.
- AI에는 실제 `SimulationState` 대신 플레이어 시야 규칙으로 만든 불변 `KnowledgeSnapshot`만 전달한다.
- 스냅샷에는 확인된 아군 상태, 현재 보이는 적, 만료 전 마지막 적 위치, 기억한 건물·지형과 추론값만 포함한다.

### 13.2 전략 계층

- 종족별 전략 점수를 계산한다.
- 난이도에 따른 재평가 간격과 전략 전환 잠금 시간을 적용한다.
- 생산, 확장, 정찰과 공격 목표를 결정한다.
- 재평가 간격은 쉬움 60초, 보통 30초, 어려움 15~20초 범위의 시드 기반 값으로 정한다.
- 전략 전환 뒤 45초 동안은 치명적 위협이나 핵심 선행 조건 상실이 아니면 다른 전략으로 바꾸지 않는다.

### 13.3 전술 계층

- 부대 구성, 대열, 태세, 경로와 후퇴를 결정한다.
- 기술 사용은 플레이어 자동 시전과 같은 평가기를 재사용한다.
- 난이도별 반응 지연 뒤 명령을 발행한다.
- 인간이 수행하기 어려운 완벽한 동시 조작을 제한한다.
- 한 전술 평가에서 발행 가능한 독립 명령 수와 부대 수를 난이도별로 제한한다.
- AI 계획과 전술 평가의 합산 예산은 한 틱 2ms, 연속 10틱 평균 1ms를 목표로 한다.
- 예산을 넘으면 낮은 우선순위 견제·재배치를 다음 평가로 미루고 현재 유효 명령을 유지한다.
- 동점 후보 선택은 AI 전용 시드 난수로 결정하고 선택 결과를 리플레이 진단 로그에 남긴다.
- AI 명령도 소유권, 자원과 시야 검증을 통과해야 하며 내부 API로 상태를 직접 변경하지 않는다.

## 14. 저장과 리플레이

### 14.1 저장 형식

- 완전한 경기 스냅샷
- 마지막 저장 이후 명령 로그
- 데이터 정의 버전
- 엔진 버전
- 체크섬
- 자동 기술, 부대 슬롯, 카메라와 선택 상태

최근 3개 저장본을 트랜잭션으로 순환 저장한다. 새 저장본 검증이 끝나기 전에 기존 정상 저장본을 삭제하지 않는다.

IndexedDB 데이터베이스 `stark-rift`는 다음 저장소를 둔다.

| 저장소 | 키 | 내용 |
|---|---|---|
| `activeMatch` | 고정 키 `current` | 이어하기에 사용할 최신 검증 저장본 |
| `saveSlots` | 자동 증가 ID | 최근 정상 저장본 3개와 체크섬 |
| `replays` | 경기 ID | 시작 헤더, 명령 로그와 탐색 스냅샷 |
| `reportOutbox` | 신고 UUID | 오프라인 신고와 첨부 전송 상태 |
| `settings` | 설정 이름 | 조작, 접근성, 그래픽과 음향 설정 |

- 자동 저장은 경기 중 10초마다, 일시정지, 백그라운드 전환과 정상 경기 종료 직전에 요청한다.
- Worker가 한 틱의 스냅샷과 체크섬을 만들고 메인 스레드가 세션 상태를 결합한다.
- 임시 레코드 쓰기, 다시 읽어 체크섬 확인, `activeMatch` 승격을 하나의 트랜잭션으로 처리한다.
- `formatVersion`, `engineVersion`, `dataVersion`, 난수·체크섬 알고리즘 버전과 압축 형식을 헤더에 기록한다.
- 스키마 마이그레이션은 원본을 보존한 복사본에 적용한 뒤 검증하며, 실패하면 마지막 호환 저장본을 유지한다.
- 용량 부족 시 오래된 리플레이와 전송 완료 신고 첨부를 먼저 정리하고, 이어하기 저장본은 자동 삭제하지 않는다.
- 손상된 최신 저장본은 격리하고 이전 순환 저장본을 제안한다.

### 14.2 리플레이

- 시작 상태, 시드와 명령 로그를 기본으로 한다.
- 빠른 탐색을 위해 일정 간격의 스냅샷을 추가한다.
- 리플레이 재생은 일반 시뮬레이션과 같은 코드를 사용한다.
- 재생 중 UI 명령은 관찰 기능만 허용한다.
- 엔진 버전이 다르고 마이그레이션할 수 없으면 호환 불가로 표시한다.
- 탐색 스냅샷은 기본 15초 간격으로 두고, 목표 틱 직전 스냅샷에서 명령을 재실행한다.
- 명령 로그는 승인된 명령과 실행 틱만 저장한다. 렌더·카메라 이벤트는 저장하지 않는다.
- 스냅샷마다 상태 체크섬을 두고 재생 중 불일치를 발견하면 해당 틱과 최초 차이 시스템을 진단 정보로 남긴다.
- 리플레이의 AI는 다시 판단하지 않고 원래 기록된 AI 명령을 실행한다.

## 15. 버그 리포트 구현

- 신고 버튼을 누르면 Worker에 원자적인 상태 스냅샷을 요청한다.
- 같은 틱의 렌더 장면, 미니맵, HUD 요약과 상태를 묶는다.
- 최근 30초 명령과 AI 결정은 고정 크기 순환 버퍼에서 추출한다.
- 네트워크가 없으면 IndexedDB 발신함에 저장한다.
- 서버는 D1에 신고 메타데이터와 상태를, R2에 큰 첨부 파일을 저장한다.
- 개발자 재현 화면은 저장된 스냅샷을 별도 디버그 시뮬레이션에 로드한다.
- 공개 게임 라우트와 개발자 신고 관리 라우트의 권한을 분리한다.

### 15.1 API와 저장 구조

| 경로 | 메서드 | 역할 |
|---|---|---|
| `/api/stark-rift/reports` | `POST` | 신고 메타데이터 발급과 첨부 업로드 정보 반환 |
| `/api/stark-rift/reports/:id` | `GET` | 익명 신고 키로 본인의 상태 조회 |
| `/api/stark-rift/reports/:id/events` | `POST` | 사용자 추가 설명 등록 |
| `/admin/stark-rift/reports` | `GET` | 개발자 목록, 검색과 처리 상태 관리 |
| `/admin/stark-rift/reports/:id` | `GET` | 장면, 진단과 재현 도구 열기 |

- D1 `stark_rift_reports`에는 ID, 익명 키 해시, 범주, 설명, 경기·엔진·데이터 버전, 틱, 상태와 생성·수정 시각을 둔다.
- D1 `stark_rift_report_events`에는 상태 변경, 개발자 메모와 사용자 추가 설명의 이력을 둔다.
- 상태는 `received`, `reviewing`, `needInfo`, `fixed`, `closed`로 제한한다.
- R2 객체 키는 신고 UUID 아래에 두고 스크린샷 WebP 1MB, 압축 스냅샷 2MB, 진단 256KB, 신고 전체 4MB로 제한한다.
- 서버는 파일 크기, MIME, 매직 바이트와 압축 해제 상한을 검증한다.
- 익명 조회 키 원문은 최초 접수 때만 사용자 기기에 저장하고 서버에는 해시만 둔다.
- 관리자 경로는 기존 `app/chatgpt-auth.ts` 인증을 재사용하고 공개 API와 권한을 공유하지 않는다.
- ChatGPT 로그인만으로 관리자 권한을 주지 않는다. 서버 환경 변수의 관리자 이메일 허용 목록을 통과한 사용자만 목록·상태 변경·첨부 열람을 허용하며 기본값은 거부다.
- IP·익명 키 기준 속도 제한과 동일 체크섬 중복 신고 묶기를 적용한다.

### 15.2 캡처와 개인정보 범위

- 캡처에는 게임 Canvas, 미니맵, 게임 HUD와 Stark Rift 진단만 포함한다.
- 다른 탭, 브라우저 주소, 계정 정보와 기기의 전체 화면은 캡처하지 않는다.
- 사용자가 전송 전에 장면, 설명, 첨부 종류를 확인하고 각각 제외할 수 있게 한다.
- 네트워크 전송 실패는 경기를 막지 않으며 발신함에서 지수 백오프로 다시 시도한다.
- 개발자 재현은 저장된 엔진·데이터 버전이 있을 때만 실행하고, 그렇지 않으면 정적 상태 검사로 제한한다.

## 16. 테스트와 검증

- 시뮬레이션 단위·속성·골든 테스트는 TypeScript 실행과 가짜 타이머가 쉬운 Vitest를 개발 의존성으로 추가해 사용한다.
- 기존 `node --test tests/rendered-html.test.mjs`는 한국어 조사와 공개 페이지 회귀 검증용으로 유지한다.
- Stark Rift 구현이 시작되면 `npm test`는 빌드, 기존 렌더 HTML 테스트와 Stark Rift 테스트를 모두 실행하도록 갱신한다.
- 테스트 데이터와 골든 체크섬은 엔진·데이터 버전과 함께 기록하며 의도한 규칙 변경에서만 갱신한다.

### 16.1 결정성

- 같은 시드와 명령으로 10,000틱 실행 후 체크섬 일치
- 저장 후 복원한 경기와 중단 없이 실행한 경기의 체크섬 일치
- 렌더 프레임률이 달라도 최종 상태 일치
- AI 난이도별 반응 지연을 포함한 반복 실행 일치
- 엔티티 ID와 논리 상태가 같다면 물리 슬롯 배치와 내부 저장소 용량이 달라도 결과 일치
- 명령 배치 크기와 Worker 전달 시점이 달라도 같은 `executeTick` 명령 결과 일치
- 서로 다른 프레임률·일시정지·저장 복원을 섞은 시드 100개 속성 테스트 통과

### 16.2 핵심 규칙

- 이동, 공격이동과 집중공격 우선순위
- 일꾼의 지역 제한 자동 채취
- 생산 집결지의 전투 유닛 공격이동과 일꾼 이동
- 5개 부대 슬롯과 최대 10기 제한
- 고지대 명중 불이익과 시야 해제
- 클로킹, 버로우와 탐지
- 자동 기술 중복 방지
- 동일 틱 본부 건물 파괴 무승부
- 수송선 파괴와 탑승 유닛 처리
- 전장의 안개와 30초 마지막 위치

### 16.3 성능

- 양쪽 최대 인구수 100
- 다수 투사체와 범위 기술 동시 사용
- 5개 부대 연합 이동과 좁은 통로 통과
- 광역 확대와 미니맵 동시 갱신
- 중급 모바일 기기에서 기본 60fps, 대규모 전투 30fps 이상
- 시뮬레이션 한 틱의 목표 CPU 시간 10ms 이하
- 메인 스레드의 긴 작업 50ms 미만
- Worker 스냅샷 전송량 기본 전투 평균 200KB/s 이하
- 경로 요청 적체가 2초 이상 지속되지 않고 시야 갱신이 틱 예산의 25%를 넘지 않음
- 10분 AI 대 AI 경기에서 메모리 증가가 초기 안정화 이후 10% 이내

### 16.4 터치 검증

- 300ms 전 개별 선택과 300ms 그룹 선택의 경계 및 250ms 응답 목표
- 빈 지형 카메라 드래그와 유닛 공격이동 스와이프 구분
- 작은 화면에서 5개 부대 슬롯 오조작 여부
- 미니맵 카메라 이동과 명령 모드 구분
- 좌우 손 버튼 교환과 큰 글자 모드

### 16.5 자동 대전과 실제 기기

- 테란·저그·프로토스 9개 대진을 난이도와 시드별로 반복해 정지 경기, 생산 막힘과 비정상 항복을 찾는다.
- 규칙 변경 전후의 평균 경기 시간, 자원 부유량, 첫 교전과 본부 파괴 시점을 비교한다.
- Android Chrome과 iOS Safari의 작은 화면·보급형·중급 기기군에서 터치, 백그라운드 복귀와 메모리 압박을 확인한다.
- 한 종족의 동일 실력 AI 승률이 45~55% 범위를 장기간 벗어나면 공개 후보로 승격하지 않는다.
- 치명 오류, 저장 손상, 진행 불가 또는 입력 유실이 한 번이라도 재현되면 해당 단계 완료를 취소한다.

## 17. 구현 단계와 완료 기준

## 18. 개발 노출 정책

- 단계 1~4 동안 정식 게임 공개 `page.tsx`를 만들지 않는다. 2026-11-11 사용자가 직접 체험을 요청한 예외로 `/stark-rift-dev` 개발 테스트를 제공한다. 메인 하단 링크·미완성 표시·검색 제외·브라우저 전용 저장 조건은 `stark-rift-hosted-preview.md`를 따른다.
- 인증이 필요한 별도 내부 도구는 서버 환경 변수로 잠근다. `/stark-rift-dev`는 기존 공개 사이트의 체험 페이지이며 비공개 접근 제어를 제공한다고 표시하지 않는다.
- 잠긴 내부 도구 라우트는 공개 빌드에서 개발 플래그가 없으면 404를 반환한다. 사용자 체험용 `/stark-rift-dev`는 이 잠금 대상에서 제외한다.
- Paperoid 정식 게임 목록과 빠른 시작에는 단계 9 완료 후 연결한다. 메인 하단의 별도 개발 테스트 링크는 사용자 요청에 따라 그 전에 제공한다.
- 공개 후 빠른 시작 순서는 `해루질럿`, `스타크 리프트`, `잉카의 다이아몬드`, `오목`, `러브레터`, `큐윅스`로 설정한다.
- `이어서 하기`가 표시되는 경우에도 `빠른 시작`을 숨기지 않는다.
- 기존 공개 게임의 동작과 빠른 시작 순서는 Stark Rift 공개 시점까지 변경하지 않는다.

- R2를 도입할 때 기존 `.openai/hosting.json` 필드를 보존하고 바인딩만 추가한다.

단계 2의 지도·카메라·렌더러와 내부 UI를 구현했다. 실제 기기의 GPU·터치 검증을 완료하기 전에는 단계 2 완료로 판정하지 않는다. 단계별 산출물과 남은 경계는 `docs/stark-rift-progress.md`에 기록한다.

1. 균열 분지의 지형·시작점·자원 데이터와 경계 검증 구현
2. PixiJS 8 렌더러와 클라이언트 수명주기 연결
3. 3단계 카메라, 미니맵과 1:2:1 내부 UI 골격 구현
4. 가시 정보 렌더 스냅샷·시야 텍스처·LOD 계약 구현
5. 화면 밖 객체 제외와 모바일 카메라 조작 검증

이 단계에서도 공개 라우트를 만들지 않는다. 투사체·이벤트·AI의 저장 스키마는 해당 게임 규칙을 구현하는 단계에서 확장한다.

## 21. 오류 처리와 사용자 복구

오류는 사용자 조작 오류, 복구 가능한 런타임 오류와 경기 지속 불가 오류로 나눈다.

| 상황 | 자동 처리 | 사용자 표시 | 진단 코드 |
|---|---|---|---|
| 잘못된 명령 | 상태 변경 없이 거부 | 짧은 이유와 진동 | `COMMAND_REJECTED` |
| Worker 응답 중단 | 일시정지 후 최신 저장으로 1회 복구 | 복구 중 표시 | `WORKER_TIMEOUT` |
| WebGL 컨텍스트 상실 | 렌더러 재생성 | 화면 복구 중 표시 | `RENDER_CONTEXT_LOST` |
| 자산 로드 실패 | 해당 묶음 2회 재시도 | 네트워크 확인과 재시도 | `ASSET_LOAD_FAILED` |
| IndexedDB 용량 부족 | 오래된 리플레이·완료 첨부 정리 | 저장 공간 부족 안내 | `STORAGE_QUOTA` |
| 저장본 체크섬 불일치 | 격리 후 이전 저장본 검사 | 이전 저장으로 복구 선택 | `SAVE_CORRUPT` |
| 프로토콜·데이터 불일치 | 로드를 중단 | 호환 불가 버전 안내 | `VERSION_MISMATCH` |
| 결정성 체크섬 불일치 | 경기 일시정지와 진단 보존 | 오류 신고·종료 선택 | `DETERMINISM_FAULT` |

- 사용자 문구는 기술 스택 이름보다 할 수 있는 다음 행동을 먼저 알려준다.
- 치명 오류에서도 마지막 검증 저장본과 버그 신고 자료를 가능한 한 보존한다.
- 동일 오류가 반복되면 자동 재시도를 멈춰 배터리 소모와 무한 루프를 막는다.
- 개발 빌드의 스택과 내부 상태는 진단 첨부에만 넣고 일반 화면에는 노출하지 않는다.

## 22. 성능 예산과 측정 지점

| 구간 | 목표 | 초과 시 우선 대응 |
|---|---:|---|
| 20Hz 시뮬레이션 한 틱 | 평균 6ms, p95 10ms 이하 | AI·경로 저우선 작업 이월 |
| 경로 탐색 | 평균 틱 예산 2.5ms 이하 | 요청 병합, 노드 예산 축소 |
| 시야·탐지 | 평균 틱 예산 2ms 이하 | 더티 영역과 마스크 캐시 점검 |
| 렌더 메인 스레드 | 60fps 기준 프레임 16.7ms 이하 | 화면 밖 제외, 효과·LOD 축소 |
| UI DOM 갱신 | 한 프레임 2ms 이하 | `uiState` 병합과 구독 범위 축소 |
| 스냅샷 직렬화·전송 | 한 틱 2ms, 평균 200KB/s 이하 | 필드 양자화, 변경분 전송 검토 |
| 자동 저장 | 사용자가 느끼는 정지 50ms 미만 | Worker 압축과 분할 쓰기 |
| 초기 상호작용 가능 | 중급 LTE에서 5초 이내 목표 | 자산 단계 로드와 캐시 |

- 개발 HUD는 시스템별 최근 평균, p95, 최댓값, 큐 길이와 엔티티 수를 표시한다.
- 성능 측정 코드는 게임 규칙에 시간을 입력하지 않고 관찰만 한다.
- Chrome Performance, Worker 타임라인과 실제 기기 메모리 측정을 단계 2·5·7·9 완료 심사에 첨부한다.
- 평균만 통과하고 긴 멈춤이 남는 것을 막기 위해 p95와 최악 프레임도 기록한다.

## 23. 보안과 신뢰 경계

- 클라이언트 저장과 리플레이는 신뢰하지 않는다. 공개 API는 크기·형식·버전·범위를 모두 다시 검증한다.
- Worker 메시지는 같은 페이지에서 왔더라도 런타임 스키마를 통과해야 한다.
- 버그 스냅샷의 파일명·설명과 압축 데이터는 서버 경로나 쿼리로 직접 사용하지 않는다.
- 관리자 신고 화면은 첨부 내용을 HTML로 해석하지 않고 다운로드 또는 격리된 뷰어에서 연다.
- 익명 신고 키, 관리자 인증 정보와 R2 서명 정보는 로그에 남기지 않는다.
- 오프라인 경기 결과는 서버 권한이나 순위에 사용하지 않는다. 추후 온라인 기능은 별도의 신뢰 모델을 설계한다.

## 27. 단계 산출물과 변경 규칙

각 단계의 PR 또는 커밋 묶음은 다음을 남긴다.

- 구현된 기획 조항과 결정 감사 ID
- 변경된 데이터·프로토콜·저장 버전
- 자동 테스트 결과와 실제 기기 확인 범위
- 성능 예산의 평균·p95와 측정 환경
- 알려진 제한, 위험 목록 변화와 다음 단계 진입 여부

프로토콜, 저장 형식과 데이터 번들의 호환 변경은 버전을 올리고 마이그레이션 또는 명확한 호환 불가 처리를 함께 구현한다. 구현 중 새 게임 규칙이 필요하면 코드에 임의로 넣지 않고 기획서, 결정 감사표와 이 설계를 먼저 갱신한다.

## 28. 최종 완료 정의

Stark Rift는 다음 조건을 모두 만족해야 공개 준비가 끝난다.

- 이전 Stark Rift·Claude 초안 코드를 복원하거나 재사용하지 않았다.
- 기획서의 세 종족 일반 대전 유닛·건물·기술과 확정 조작 규칙이 구현됐다.
- 플레이어 대 AI 오프라인 경기를 시작, 일시정지, 저장, 복구하고 정상 종료할 수 있다.
- 같은 시드와 명령의 결정성, 저장 복원과 리플레이 체크섬 검증이 통과한다.
- 최대 인구 100 대 100 교전에서 시뮬레이션·렌더링·메모리 예산을 충족한다.
- 실제 모바일에서 선택, 카메라, 미니맵, 5개 부대, 기술과 수송 조작 검증을 통과한다.
- 평균 경기 시간 8~12분과 동급 AI 종족 승률 45~55% 목표를 검증했다.
- 튜토리얼, 접근성, 최종 자산, 음향과 오류 복구 흐름이 완성됐다.
- 장면·상태 첨부 버그 신고와 개발자 상태 관리가 동작한다.
- 기존 Paperoid 게임과 한국어 조사 테스트를 포함한 전체 빌드·테스트가 통과한다.
- GitHub `main`, Sites 내부 소스와 실제 저장 버전이 같은 검증 커밋을 가리킨다.
- Paperoid 메인, 전체 게임 목록과 빠른 시작 연결은 위 조건을 통과한 뒤 한 번에 공개한다.

## 29. 검토에서 발견한 남은 결정

기존 대화의 확정 사항은 모두 반영돼 있다. 다음 항목은 구현 계약을 대조하는 과정에서 새로 드러난 세부 선택이며 관련 단계에 들어가기 전에 결정한다.

| ID | 결정할 내용 | 영향 단계 | 현재 권장안 |

| O-01 반영 | 자원·인구수가 부족한 생산 명령의 접수, 비용 예약과 반복 생산 우선순위 | 단계 4 | 2026-11-11 권장안 적용. 실행 틱 비용·인구 예약, 사용자 대기열 우선, 비었을 때 반복 한 주문 보충. 상세 계약은 `stark-rift-stage4-plan.md` |
