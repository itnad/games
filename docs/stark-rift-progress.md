# Stark Rift 단계별 구현 기록

## 단계 1 — 결정적 엔진 기반

구현일: 2026-11-01. 엔진 `0.3.0-stage1`, 스키마·저장·통신 버전 3.

### 구현한 내용

- `fixed-point.ts`: 1타일=256, 20Hz/50ms 상수, 안전 정수 덧셈, BigInt 중간 곱셈과 0 방향 나눗셈, 부호 있는 이동 나머지 누적. 음수 0을 정규화한다.
- `rng.ts`: SplitMix32 시드 전개와 xoshiro128**. 전투·AI·지도·규칙 스트림의 상태를 경기 데이터에 보존한다.
- `world.ts`: 정렬된 ID와 소유자·정의 ID·위치·체력의 병렬 배열. 삭제한 ID를 재사용하지 않으며 2,048개 한도와 정수 고갈을 검사한다. 투사체와 이벤트 ID도 동일한 카운터 할당 함수를 사용한다.
- `simulation.ts`: 14단계 고정 시스템 실행 순서, 명령 예약, `(executeTick, playerId, sequence)` 정렬, 중복 방지, 실행 시 소유권·생존 재검증, 명령 핸들러별 부분/전체 실행 정책, 항복과 일시정지 상태 처리.
- `clock.ts`: 프레임 시간과 시뮬레이션 상태를 분리한 고정 틱 어댑터. 기본 5틱 catch-up 후 남은 시간을 보존하며 정지 상태에서 누적 시간을 비운다. UI의 일시정지 전환 시 `reset()`한다.
- `checksum.ts`: 키 순서에 의존하지 않는 정수 JSON 직렬화와 UTF-8 xxHash32. 공식적으로 알려진 짧은 입력·16바이트 이상 입력의 벡터를 검사한다.
- `state.ts`: 실행 중 상태 저장·복원, 독립된 복사본 생성, 전체 경기 상태 체크섬 검증, 버전·소유자·카운터·예약 명령·난수 스트림의 일관성 검사. 카메라·선택·저장 시각은 경기 체크섬에서 제외한다.

### 단계 완료 검증

- 렌더러나 브라우저 없이 Node/Vitest에서 실행한다.
- 엔티티 10개, 독립 난수 스트림, 예약 명령과 테스트용 상태 변경 시스템을 사용해 10,000틱을 두 번 실행한다. 100틱마다 상태 체크섬을 대조한다.
- 4,300틱에 저장·직렬화·복원한 실행을 끝까지 비교한다. 9,000틱의 미래 명령과 명령 중복 방지 상태가 복원되는지도 검사한다.
- 위조된 체크섬, 재계산한 체크섬을 가진 잘못된 소유자, 수치 오버플로, 부분/전체 실행 정책과 시스템 실행 순서를 검사한다.
- 엔진 테스트의 이동 핸들러와 난수 상태 변경은 **테스트 전용 규칙**이다. 실제 RTS 이동이나 전투가 완성됐다는 의미가 아니다.

### 현재 경계와 다음 단계

단계 2는 지도 데이터, PixiJS 렌더러, 카메라·미니맵·시야 텍스처와 1:2:1 UI 골격이다. 이후 단계에서 선택·경로 탐색·경제·전투·AI를 순서대로 연결한다.

- 실제 게임 명령은 관련 단계의 핸들러가 등록되기 전까지 거부한다. 엔진이 실행하지 않은 명령을 성공으로 처리하지 않는다.
- 투사체·효과·예약 이벤트·AI 저장소는 아직 빈 계약이다. 관련 단계에서 스키마와 호환 버전을 함께 확장한다.
- 초기 엔티티 저장소는 JSON으로 직접 보존 가능한 정렬된 compact SoA 배열이다. TypedArray 용량 풀과 희소 컴포넌트는 실제 렌더/전투 부하를 측정할 때 도입한다.
- 원작 수치 데이터 번들과 해시는 콘텐츠 단계에서 생성한다. 현재 `stage1-unbuilt` 표시는 게임 콘텐츠가 아직 없다는 뜻이며 기획 수치를 임의로 만들지 않는다.
- 실제 Worker 실행 어댑터·백그라운드 처리·IndexedDB·리플레이 UI는 아직 구현하지 않았다.
- 이 단계에서는 공개 라우트를 생성하지 않는다. 실제 기기 성능과 60fps는 아직 검증 대상이 아니다.

기획 결정 추적: 감사표의 자유 이동·기존 구현 미재사용 원칙과 구현 설계 §4~6, §16~17을 따른다. O-01~O-03의 보류 결정은 변경하지 않았다.
