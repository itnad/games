# Stark Rift 개발 기반 검토와 보강

> 검토일: 2026-11-01
> 검토 대상: `d9b7e88759001e121f6226acc5cf102e2844b30b`의 단계 0
> 판정: 기존 단계 0은 명칭과 타입 골격 중심이었다. 아래 보강 후 단계 1 개발의 입력 경계로 사용한다.

## 발견한 문제와 처리

| 문제 | 보강 |
|---|---|
| 이동 목적지·생산 유닛·기술 ID 없이도 명령 접수 | 23개 명령을 판별 유니온으로 정의하고 종류별 대상·payload 필수화 |
| 타입 선언과 입력 검증의 규칙이 따로 존재 | 명령·양방향 메시지·데이터 타입을 런타임 스키마에서 도출 |
| 빈 선택·중복 엔티티·동일 틱 실행 허용 | 항복을 제외한 대상 필수, 중복 거부, `executeTick > issuedTick` |
| 초기화에 플레이어 ID만 존재 | 종족과 사람/AI 설정을 필수화하고 1대1의 서로 다른 두 플레이어 검증 |
| 명령 배치의 중복·비정상 크기 미검증 | `(playerId, sequence)` 중복, 미래 발행 틱, 최대 256개 제한 검사 |
| Worker 응답은 임의 객체 | 지원하는 8개 응답의 payload를 런타임과 타입 양쪽에서 검증 |
| 저장 불러오기는 객체 여부만 검사 | 봉투·세션·현재 단계의 상태·UTC 시각·버전·알고리즘 검사 |
| 저장 봉투가 원본 상태를 참조 | 검증 후 `structuredClone`으로 독립된 스냅샷 생성 |
| 데이터가 ID만 있어도 통과 | 비용·시간·체력 등 기본 필드, 선행 조건·생산처·능력 참조, 순환 선행 조건 검사 |
| 지도 시작 위치 미검증 | 지도 경계와 중복 시작 위치 검사 |
| 원본 수치·변환 기준이 코드에 없음 | 번들 헤더에 Brood War 1.16.1, 20Hz, 시간 비율 1/2 명시 |
| 테스트가 정상적인 작은 예제 중심 | 모든 명령·메시지와 잘못된 입력, 저장 독립성, 데이터 관계의 회귀 사례 추가 |

## 고정한 통신 표현

- 엔진 버전은 `0.2.0-stage0`, 데이터 스키마·저장 형식·통신 버전은 모두 2다. 기존 버전 1은 명시적으로 거부한다. 공개 경기 저장본은 아직 없다.
- 명령 번호 `sequence`는 1부터 시작한다. `messageId`와 플레이어 ID는 0부터 허용한다.
- 명령당 엔티티 최대 200개와 배치당 명령 최대 256개는 전송 예산이다. 실제 인구·조작 규칙은 엔진이 별도로 적용한다.
- `setFormation.payload.formation`: `line`=전열, `column`=종대, `spread`=분산.
- `setStance.payload.stance`: `free`=자율 교전, `formation`=대열 유지, `breakthrough`=목표 돌파.
- 생산은 `unitId`, 건설은 `buildingId`, 연구는 `technologyId`, 기술은 `abilityId`를 전달한다.
- 토글은 재전송으로 반전되지 않도록 `enabled: boolean`으로 원하는 상태를 명시한다.
- 생산 취소는 배열 위치가 아니라 안정적인 `queueEntryId`를 사용한다.
- 자기 자신에게 쓰는 기술도 `target: { kind: "self" }`를 전달한다. 실제 기술별 대상 허용 여부는 엔진에서 다시 검사한다.
- 개별 하차는 수송선 하나, `passengerId`, 목적 지점을 전달한다. 현재 위치 하차도 UI가 명시적인 좌표로 보낸다.
- `renderSnapshot`, `uiState`, `notification`은 예약된 응답이다. 렌더러·UI 단계에서 구체적인 스키마를 만들기 전에는 유효한 메시지로 수락하지 않는다.
- 모든 객체는 알 수 없는 필드를 거부한다. `NaN`, 무한대, 소수 ID, 안전 정수 범위 밖 수, 배열의 빈 칸과 상속 필드를 유효한 값으로 취급하지 않는다.

## 보강 범위의 한계

이 변경은 게임 엔진·게임 화면을 구현하지 않는다. 다음 항목을 이미 완료된 기능으로 해석하면 안 된다.

- 저장 검증은 **단계 0의 setup/tick 0과 비어 있는 엔티티·투사체·효과·예약 이벤트·AI 저장소**만 지원한다. 엔진 단계에서 구체적인 저장소 레이아웃과 의미 검증을 정의한 뒤 호환 버전을 갱신한다. 임의 객체를 정상적인 경기 저장본으로 승인하지 않는다.
- 체크섬은 알고리즘 이름과 8자리 16진수 형식만 검사한다. 실제 xxhash32 계산·내용 일치·직렬화·압축·IndexedDB는 단계 1 및 단계 8 작업이다.
- 난수 상태의 4개 Uint32와 전부 0인 상태를 검사하지만 난수 생성기 자체는 없다.
- 데이터 스키마는 공통 비용·내구도·무기 기본값·참조·지도 크기와 시작점까지의 초기 계약이다. 실제 원작 수치 원본, 데이터 해시 생성, 범위 피해·생산/변태 예외·지형·자원·대칭 검증은 관련 구현 단계에서 추가한다. 테스트 수치는 계약 검사용이며 원작 수치 원본으로 사용하지 않는다.
- 메시지 형식 검증은 소유권·실제 시야·자원·사거리·현재 상태·명령 종류별 부분 실행 정책을 판단하지 않는다. 경기 상태를 가진 단계 1 이후의 검증기가 수행한다.
- `metrics`는 관찰 횟수와 개수의 초기 계약이다. 실제 틱 처리시간, p95와 성능 기준은 엔진이 생긴 후 측정한다. 빈 함수 성능으로 완료 판정을 내리지 않는다.
- 실제 기기·브라우저 검증은 실행할 게임 화면이 없는 이번 변경의 검증 범위 밖이다.

## 검증과 재개 순서

1. `npm run test:stark-rift`: 전용 타입 검사와 계약 테스트.
2. `npm test`: 전체 빌드, 기존 게임/한국어 조사 회귀 테스트, Stark Rift 테스트.
3. `.github/workflows/stark-rift.yml`: 푸시·PR에서 같은 명령을 실행한다.
4. 단계 1에서는 고정소수점·ID·난수·명령 스케줄러·실제 상태 저장소를 먼저 구현한다.
5. 결정적 20Hz 엔진을 만든 후 10,000틱 반복, 상태 직렬화와 저장·복원 체크섬 일치를 검증한다.

기존 기획의 187개 결정과 보류 항목 O-01~O-03은 유지한다. 특히 자원 부족 생산 명령, 시야에서 사라진 집중공격 대상과 그룹 선택 반경의 게임 규칙을 이번 검증 코드로 새로 결정하지 않는다.
